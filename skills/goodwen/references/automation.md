# 定时、事件与持续跟进

时间调度、唤起、通知和 Dots 由宿主提供，Goodwen 保存领域事实、处理进度与成果。先核对目标会话的真实任务和插件能力；不要从包内有 Skill 推断宿主已支持自动执行。

## 建立安排

1. 沿用明确的工作区、问卷、版本范围和处理目的。补齐会改变执行结果的时间／事件条件、时区、送达位置与停止条件，已有信息不重复询问。
2. 按[批量与成果恢复](processing.md)建立稳定的 Goodwen 处理任务，把真实 `workspace_id`、`pack_id`、可选 `release_id`、`task_id/reference`、目的版本及评分要求写入宿主保存的任务指令。不能只保存问卷名称或依赖旧卡片。
3. 用宿主任务能力创建、复用或更新安排，再核对实际返回的任务引用、触发条件及状态。把执行时间和时区向用户说清；宿主提供管理入口时返回该入口。
4. 默认持续处理积压、尚未完成及后续新增回答。用户限定固定起点时保存该起点；每轮使用新的运行键，复用成果，不推进宿主时间水位。

## 时间任务与 Dots

ChatGPT 的 Scheduled 可按真实可用能力运行插件；返回原会话时保存该会话的送达要求。Dots 适合持续上下文与后续跟进，仍需确认实际接入的插件、执行主体和审批。桌面本地执行是否要求设备在线，按当前宿主设置判断；云端任务不能依赖本机临时文件。

时间与事件是两种触发；不能假定同一任务同时支持两者。用户需要每日汇总和事件跟进时分别建立安排，可复用同一 Goodwen 处理成果。WorkBuddy 沿用其自身提供的能力，不套用 ChatGPT 的 Scheduled／Dots 操作。

## 新回答事件

在支持 MCP Events 的宿主中，发现并订阅 `response.submitted`。ChatGPT 对应网页版 Work、桌面 Work 的 Cloud 模式和 Dots，具体可用性受账号与工作区设置限制。

- `events/list` 发现事件目录，不计入35个业务工具，不要求先指定工作区。
- `events/subscribe` 的 `arguments` 传入选定的 `workspace_id`、`pack_id` 和可选 `release_id`，需要 `results:read`、`events:subscribe`。回调 URL 与签名密钥由宿主提供，不向用户索取，不写入任务正文或回复。
- 以服务返回的 `id`、`refreshBefore` 和 `cursor` 核对安排，在期限前续订同一主体、范围和回调。需要回放时使用返回游标；重复事件保持稳定 `eventId`，按该 ID 去重。
- 事件只有引用，没有答案或评分规则。收到事件后按当前权限重新读取，并执行已保存的处理要求；按宿主能力合并相近事件，不把每个事件变成重复提醒。
- 订阅成功只说明交付安排成立；回调接收不代表分析、保存或通知已完成。分别核对这些阶段。
- 用户停止事件跟进时执行真实 `events/unsubscribe`，保持相同 `arguments` 与回调地址；取消可省略 secret。关闭页面、结束对话或暂停一个时间任务不等于取消事件订阅。

宿主不支持事件时，说明该限制。用户要求事件触发时，不把一个轮询提醒冒充事件订阅；已获授权的定时方案或人工续做可按实际能力继续。

## 每轮交付与暂停恢复

每轮先处理、保存，再交付新发现、个人下一步与准确链接。用户要求的汇总在同轮完成，不要求收到提醒后再点击“分析”。没有新增且没有待完成项时，按用户的静默要求结束；周报、累计趋势和固定交付任务仍完成已约定的内容。

授权失效、读取失败、宿主审批和保存失败分别说明，不能把失败当作没有新增。能回复时先交付可用分析，并准确标明未写入的评分／成果；恢复后只补缺少的步骤。宿主整个运行暂停时，不承诺还能先发通知。

暂停、恢复和取消按原触发方式更新实际安排，保留已保存成果。团队任务以所用应用连接的真实 OAuth 主体校验权限，不用任务创建者姓名代替业务身份。

## 可复用的用户请求

> 每个工作日北京时间上午9点，处理这份问卷积压及新增的未完成回答，复用已保存成果，给出逐份建议和本轮结论。结果回到本会话，没有新发现不通知，持续到我暂停。

> 这份需求问卷有新回答时就分析：归纳新主题、分歧和下一次访谈重点，保存分析并把有用发现发回本会话，不另外联系回答者。

> 暂停刚才的每日任务，保留已有分析；恢复时接着处理积压。停止事件跟进时取消对应订阅。
